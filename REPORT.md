# AI-Powered Student Virtual Assistant - Practical Report

## 1. Problem Statement

College students regularly get stuck on academic topics, programming concepts and study planning
outside class hours, when teachers and classmates are not available. Searching the web returns
material of mixed quality and level. This project builds a small virtual assistant that answers
such questions in simple, student-friendly language.

## 2. Objectives

1. Build a working chat application where a student types a question and receives an answer.
2. Use a Generative AI model with a clear educational system prompt.
3. Keep conversation history so follow-up questions work, and allow it to be cleared.
4. Show a loading indicator and handle errors without crashing.
5. Keep the API key secret (environment variable, server-side only).
6. Provide a clearly labelled demo mode so the app can be run and tested without credentials.
7. Test with representative inputs, including a vague one, and record the real results.
8. Identify one limitation of the system and propose an improvement.

## 3. Technology Used

| Component | Choice |
|---|---|
| Language | Python 3.10+ |
| User interface | Streamlit (text input, Send button, chat view, sidebar) |
| Generative AI | Anthropic Claude API via the `anthropic` Python SDK (model configurable, default `claude-sonnet-5-5`) |
| Configuration | Environment variables / `.env` file loaded with `python-dotenv` |
| Testing | `run_tests.py` (plain Python), results saved to `results/` |

## 4. Prompt and Context Design

The system prompt (`SYSTEM_PROMPT` in `assistant.py`) tells the model:

- **Role and audience:** a friendly, patient tutor for undergraduate students.
- **Scope:** academic topics, programming concepts and study skills.
- **Answer style:** plain-language answer first, define jargon, use an everyday analogy, include a short
  runnable code example for programming, usually under 250 words, end with a summary or check question.
- **Honesty rules:** if the question is vague or refers to unseen context (e.g. "Explain it"), ask one
  clarifying question instead of guessing; admit uncertainty; never invent facts, citations or URLs.
- **Academic integrity:** explain and give hints rather than writing complete assignments.
- **Privacy and safety:** remind students not to share sensitive data; respond kindly to distress and
  point to a counsellor; decline harmful or unrelated requests.

Context sent with each request: the system prompt plus the last 20 messages of the conversation
(so follow-ups work while keeping requests small). Output is limited to 1024 tokens.

## 5. Implementation

- `assistant.py` - core logic with no UI code: system prompt, `generate_reply()`, live API call,
  demo mode, and translation of API errors into friendly messages.
- `app.py` - Streamlit interface: sidebar status banner, three example-question buttons, chat history,
  a form with a text input and **Send** button, a spinner ("Thinking...") during the call,
  error bubbles, and a **Clear conversation** button.
- Key handling: `ANTHROPIC_API_KEY` is read with `os.getenv` on the server. It is never written into
  the page, logged, or included in error messages. `.env` is in `.gitignore`; `.env.example` holds a placeholder.
- Demo mode: when no (or a placeholder) key is found, replies come from a few fixed texts. Each is prefixed
  with "DEMO MODE - NOT generated by an AI model", the sidebar shows a warning, and a caption appears under each reply.
- Input validation: empty input shows a warning; input over 2000 characters is rejected.

> **Synchronous vs asynchronous JavaScript**
> 
> - **Synchronous** code runs line by line; each line must finish before the next starts.
> - **Asynchronous** code lets slow work (timers, network requests) happen in the background while the rest of the program keeps running.
> 
> ```javascript
> console.log("1: Start");
> setTimeout(() => console.log("2: Timer finished"), 1000);

> ```

> async function loadUser() {

> }
> ```

> 
> **Summary:** synchronous = wait and then continue; asynchronous = start the task, keep working, handle the result when it arrives (callbacks, Promises, async/await).

## 8. Limitation

**Hallucination / accuracy.** A generative model produces text that *sounds* right based on patterns, and
it can state wrong facts, formulas or code with complete confidence. A student who is still learning the
topic often cannot tell, so the error could be memorised and repeated in an exam. The assistant also has
no access to the student's own syllabus or textbook, so its explanation may differ from what the course expects.
(A related privacy point: in live mode the questions are sent to an external AI provider, so students must
not enter personal data.)

## 9. Suggested Improvement

Add **retrieval-augmented generation (RAG)** over trusted course material. The student (or teacher) uploads
lecture notes or a textbook PDF; the app splits it into chunks, finds the chunks most relevant to the question,
and gives them to the model with an instruction to answer *only from them* and to cite the page or section.
If nothing relevant is found, the assistant says so. Combine this with a visible reminder such as
"Verify important answers with your textbook" and, for code answers, an option to run the example
before trusting it.

## 10. Conclusion

The project delivers a complete prototype: a Streamlit chat interface with history, example questions, a
loading indicator, error handling, a clearly labelled demo mode, and a live-AI path that keeps the API key on
the server. In the build environment, only the demo-mode behaviour and the application logic could be
verified; the Streamlit screenshots and the live AI test results still have to be produced on a machine with
internet access and an API key, using the steps in `README.md`. Even then, the assistant is a study aid and not
an authority - its answers should be verified, which motivates the proposed course-material-grounded improvement.

# Project Report — Smart Notes (Smart Note-Taking Application)

**Subject:** Web Development Practical
**Date of testing:** 19 October 2026
**Environment used:** Windows · Google Chrome · Python 3.15 (`http.server`) · Node.js 24 (test runner only)

---

## 1. Objective

To design and implement a complete, working smart note-taking application that
lets a student create, edit, organise, search, pin and delete notes, and keep
them permanently in the browser using `localStorage` — using only HTML, CSS and
JavaScript so that the project stays simple to understand, run and submit.

**Secondary objectives**

* Deliver a modern, responsive and accessible user interface.
* Confirm every destructive action before performing it and show meaningful
  empty states instead of blank screens.
* Verify every feature by actually running the application (not by inspection
  alone) and record genuine screenshots.

---

## 2. Technologies Used

| Layer | Technology | Purpose |
|-------|------------|---------|
| Structure | HTML5 | Page layout, forms, dialogs (`role`, `aria-*` attributes) |
| Styling | CSS3 | Flexbox + CSS Grid, custom properties, transitions, `@media` breakpoints (900 px / 560 px) |
| Behaviour | Vanilla JavaScript (ES6) | State management, rendering, event delegation, `localStorage` persistence |
| Storage | Web Storage API (`localStorage`) | Persistent notes, folders and UI preferences |
| Hosting | Python `http.server` (or opening `index.html` directly) | Static file serving |
| Testing / screenshots | Chrome DevTools Protocol via `tests/capture.mjs` (headless Chrome) | Automated UI runs, DOM-state verification, screenshot capture |
| AI Engine | Native Client-Side NLP + Cloud APIs | Extractive summarizer, TF-IDF keyword extractor, task parser, study generator; optional Gemini/OpenAI cloud connector |

No heavy frameworks, bundlers or external CDNs are required.

---

## 3. Features Implemented

1. **Create / edit / delete notes** — modal form with title, content, folder,
   tags and pin flag; inline validation; ✎ edit pre-fills every field.
2. **Search** — instant, case-insensitive search across title, content and tags,
   with a clear (✕) button and a filter pill.
3. **Organisation** — folders (create, filter, delete with confirmation) and
   tags (auto-generated tag cloud with counts, click to filter).
4. **Pin / unpin** — pinned notes get a badge, float to the top of every list
   and are counted separately in the *Pinned* view.
5. **Persistence** — all notes/folders/UI state written to `localStorage`
   (`smartnotes.v1.notes`, `.folders`, `.ui`, `.ai_settings`) on every change.
6. **Responsive UI** — sidebar collapses to a horizontal bar and a floating
   action button appears below 900 px; single-column cards below 560 px.
7. **Safety & empty states** — confirmation dialog for delete, delete-forever,
   empty-trash and folder deletion; dedicated empty states for "no notes",
   "no search results", "empty folder" and "empty trash"; toast notifications.
8. **AI Note Copilot** — in-editor toolbar providing:
   * **✨ Title Generation**: auto-generates descriptive titles from note text.
   * **🏷️ Auto-Tags**: extracts key topic keywords as tags.
   * **📝 Summarize**: extracts and appends executive key takeaways.
   * **🪄 Polish**: improves readability, grammar, punctuation, and flow.
   * **✅ Action Items**: extracts todos, deadlines, and imperatives into checklist boxes.
   * **📚 Study Guide**: reformats notes into Cornell-style study sheets with review questions.
   * **⚡ Reading Metrics**: live word count and estimated reading time.
9. **AI Library Assistant (`Ctrl+J`)** — multi-note intelligent Q&A drawer:
   * Answers questions across the student's note library.
   * Extracts all pending tasks across every note.
   * Generates interactive study quizzes based on saved notes.
   * One-click "Save as Note" and "Copy" actions.
10. **Dual-Engine Architecture** — instant 100% offline local AI out of the box,
    plus in-app configuration for Google Gemini / OpenAI cloud LLMs.
11. **AI Card Insights** — instant modal insight with executive summary, action
    items, and recommended tags directly from note cards.

Extras: 3 sort orders, trash with restore, keyboard shortcuts
(`Ctrl+K`, `Ctrl+N`, `Ctrl+J`, `Esc`, `Enter`), corrupted-storage recovery.

### Bugs found during testing and fixed

1. **Dialogs visible on page load** — `.overlay { display:flex }` overrode the
   HTML `hidden` attribute, so the modal and confirm box were rendered on top of
   the page. Fixed with a global `[hidden] { display:none !important; }`.
2. **Folder delete control was unreachable** — the ✕ was a `<span>` nested
   inside a `<button>` (invalid HTML, not keyboard/assistive-technology
   reachable). Re-structured as a sibling `<button>` with an accessible name
   (“Delete folder College”).
3. **Folder name input used `window.prompt`** — replaced with an in-app dialog
   (validation, `Enter`/`Esc`, focus handling) for better UX and testability.
4. **Empty folder looked like a failed search** — the “No notes match …” screen
   was shown for a folder with zero notes; now the friendlier
   “This folder is empty” state is displayed.
5. **Grammar in the empty-trash confirmation** — “All 1 note …” changed to
   “The 1 note …”.

## 6. Limitations

* **Storage is local to the browser/profile** — no cloud sync, no accounts;
  clearing site data or switching device/browser loses the notes.
* **`localStorage` quota** (≈ 5 MB) — very large numbers of long notes can hit
  the limit; the app shows a warning instead of failing silently.
* **Plain-text notes** — no Markdown/rich text, images, checklists or file
  attachments; content is capped at 5 000 characters and titles at 120.
* **Search is simple substring matching** — no fuzzy matching, relevance
  ranking, highlighting or date-range filters.
* **No export/import, versioning or undo** beyond the Trash (restore) flow.
* **Not encrypted** — data is readable by anyone with access to the browser
  profile.
* **Testing coverage** — screenshots were taken in Chrome; other browsers and
  older browser versions were not formally tested.
